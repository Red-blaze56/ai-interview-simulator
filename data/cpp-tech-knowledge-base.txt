Conclusions are uniformly attributed using the following markers:

- **[Language Standard]**: Portable semantics specified by the C++ language standard. When no version is marked, this means core semantics that still hold from C++11 onward; capabilities newly added in specific versions are noted separately.
- **[Compiler/Standard Library Implementation]**: Strategies of compiler optimization, code generation, or a particular standard library implementation — not physical structures or fixed constants that all implementations must adopt.
- **[Platform/ABI]**: Target architecture, data model, calling convention, object ABI, linker, and binary compatibility constraints. Conclusions must be bound to a specific target triple and ABI.
- **[OS/Allocator]**: Behavior of kernel APIs, libc, general-purpose allocators, or alternative allocators. Thresholds, caches, reclamation, and RSS behavior must be bound to version, configuration, and workload.

Interview evaluation priority: correct standard semantics > ability to distinguish implementation boundaries > ability to analyze lifecycle and concurrency correctness > ability to verify with tools and evidence. A candidate who proactively states "the standard doesn't specify this; the target ABI, implementation, or profile must be checked" is usually more valuable than reciting fixed addresses, multipliers, thresholds, and structure fields.

## 1. Basic Semantics, Storage Duration, and Linkage

### Basic Questions and Answer Points

#### Pointer Size, Null Pointers, Wild Pointers, and Dangling Pointers

**Are pointers always 4 or 8 bytes?**

- **[Language Standard]** Not necessarily. The standard only requires that a pointer can represent addresses allowed by its type and states like the null pointer; it does not specify a fixed value for `sizeof(T*)`, nor does it guarantee that object pointers and function pointers have the same size or representation.
- **[Platform/ABI]** On common 32-bit or 64-bit platforms, ordinary object pointers are often 4 or 8 bytes respectively, but segmented addresses, capability pointers, special address spaces, and function descriptors can all produce different results.
- `sizeof(p)` measures the pointer object itself; `sizeof(*p)` measures the pointed-to type; arrays decay to a pointer to the first element in most expressions, but `sizeof(array)` is still the size of the whole array.
- A null pointer value is not equal to "the standard guarantees all bits are zero". `nullptr` has type `std::nullptr_t` since C++11 and should be preferred over integer `0` and macro `NULL` in overload resolution.

**What is the difference between wild, dangling, and null pointers?**

- A wild pointer usually refers to an uninitialized pointer or one holding an invalid address; reading an uninitialized pointer can itself produce undefined behavior.
- A dangling pointer once pointed to a valid object whose lifetime has ended — e.g., returning the address of a local object, retaining an old address after container reallocation, or continuing to hold the original pointer after `delete`.
- A null pointer explicitly points to no object and can be compared and passed; dereferencing a null pointer is undefined behavior. Assigning a freed pointer to `nullptr` only reduces the risk of misuse of the current variable; it cannot fix other aliases.
- The key prevention points are ownership, lifetime, and invalidation rules — not mechanically "setting all pointers to null after every free".

#### Pointers, References, and `const`

**What are the standard semantic differences between pointers and references?**

- **[Language Standard]** A reference must bind at initialization and cannot be "re-bound" later via assignment; assigning to a reference actually assigns to the referenced object. A pointer is an object: it can be null, change what it points to, and participate in constrained pointer arithmetic.
- **[Language Standard]** Expressions like `sizeof(ref)` and `typeid(ref)` typically observe the referenced type or object; you cannot conclude from them that "references never occupy memory on the machine".
- **[Compiler/Standard Library Implementation]** Local references can often be completely eliminated and need no independent storage.
- **[Platform/ABI]** When a reference is a data member, passed across function boundaries, or requires stable object layout, the ABI often implements it as an address-like representation; its member size, padding, and calling convention are determined by the target ABI. The reference's abstract semantics and physical storage must be answered separately.
- A reference in a well-formed program should bind to an object or function; fabricating a "null reference" via dereferencing a null pointer is already undefined behavior — it cannot be treated as references supporting null values.

**What are `const T*`, `T* const`, and `const T* const`?**

- `const T* p` or `T const* p` is a pointer to const: you cannot modify `T` through `p`, but `p` can change what it points to.
- `T* const p` is a const pointer: `p` cannot change what it points to, but you can modify the non-const `T` through it.
- `const T* const p` restricts both changing the pointer and modifying the object through it.
- Top-level `const` qualifies the object itself; bottom-level `const` belongs to the pointed-to type. Top-level `const` on by-value parameters does not produce a different function type; bottom-level `const` affects type conversion and overloading.
- `const_cast` only changes the cv-qualification of the access path. If the original object is actually defined as const, writing through a de-consted path is undefined behavior.

#### Value, Pointer, Reference Passing and Lifetime

**How to choose between value, pointer, and reference parameter passing?**

- Pass by value for small copyable values or when an independent copy is needed; the caller can provide the argument by copy or move. Whether an actual copy occurs depends on language semantics and copy elision.
- Use a pointer, smart pointer, or explicit optional-like type when a default target is allowed; a raw pointer parameter usually indicates non-owning and ownership transfer should not be inferred from the type alone.
- Use `T&` when you must reference an existing object without taking ownership; use `const T&` for read-only borrows. For small scalars, pass-by-value is usually more direct than `const T&`.
- To take ownership, prefer receiving `std::unique_ptr<T>` by value or an explicit owning type; only pass `std::shared_ptr<T>` for shared ownership — do not default to sharing to avoid writing lifetime rules.
- `std::span` (C++20) and `std::string_view` (C++17) are non-owning views. Copying a view does not extend the underlying object's lifetime; returning a view pointing at local or temporary data dangles.

**Does binding a temporary to a reference always extend its lifetime?**

- **[Language Standard]** When a temporary is directly bound to certain local `const T&` or `T&&`, its lifetime may be extended to that of the reference, but the rules depend on the initialization context.
- Passing the reference on to another function, storing it in a reference member, or returning it from a function typically does not extend the original temporary's lifetime again.
- A temporary bound to a function parameter reference typically lives only until the end of the full-expression containing the call; returning that parameter reference leaves a dangling reference.
- Return value optimization and moves cannot make a raw pointer, reference, or view pointing at a local object safe; return a value that owns the object.

#### Scope, Storage Duration, and Linkage

**Why can't scope, storage duration, and linkage be conflated?**

- **[Language Standard]** Scope answers "where is the name visible in source code"; storage duration answers "from when to when does the object's storage exist"; linkage answers "whether declarations in different scopes or translation units refer to the same entity".
- Automatic storage duration objects are usually created on entering a block and destroyed on leaving, but the exact lifetime is also affected by successful initialization, exception unwinding, and temporary object rules.
- Static storage duration objects' storage covers the entire program execution, including namespace-scope objects and function-local `static`; initialization and destruction order still need separate analysis.
- Thread storage duration objects (`thread_local`) have an instance per thread; their initialization timing and thread-exit destruction affect dynamic library unloading, thread pools, and shutdown.
- Dynamic storage duration comes from a `new` expression or other explicit lifetime management; "dynamic" does not mean it must be implemented by a fixed data structure of the libc heap.

**What does `static` express in different positions?**

- A `static` name at namespace scope has internal linkage and only associates within the current translation unit.
- A `static` object at block scope has static storage duration, but the name still has only block scope.
- **[Language Standard, since C++11]** Function-local static initialization has thread-safe guarantees: concurrent first entry completes only one initialization; recursion, blocking, and exceptions inside the initialization function still need analysis.
- A class static data member does not belong to each instance. Traditional non-inline members usually need an out-of-class definition; C++17 `inline static` data members can be defined in-class.

#### Header Definitions, ODR, `inline` Variables, and `extern "C"`

**Why shouldn't ordinary non-`inline` functions or variables be defined directly in public headers?**

- **[Language Standard]** The One Definition Rule (ODR) requires a specific entity to have only one definition throughout the program; certain entities such as classes, templates, inline functions, and inline variables may appear in multiple translation units with definitions satisfying strict equivalence conditions.
- When a header is included by multiple translation units, ordinary external-linkage definitions form multiple definitions; include guards only prevent the same translation unit from including repeatedly and cannot solve cross-translation-unit ODR.
- Template and inline definitions are usually placed in headers so every point of use sees them; multiple definitions must satisfy ODR conditions like token and name-lookup equivalence. Macros can make different translation units see different definitions, potentially forming ill-formed, no diagnostic required problems that are hard to diagnose.
- Namespace-scope non-volatile `const` variables often have internal linkage by default, but this should not be treated as a design device for freely copying stateful objects into headers.

**Does `inline` mean the compiler will definitely inline?**

- **[Language Standard]** The core language function of `inline` is to permit multiple definitions satisfying conditions and indicate the same entity; it does not promise that machine-code calls will be expanded.
- **[Compiler/Standard Library Implementation]** Whether inline optimization occurs is decided by the compiler based on optimization level, LTO, profile, function body, and debugging requirements; functions without `inline` may also be optimized inline.
- **[Language Standard, since C++17]** An inline variable can be defined in multiple translation units and represent one entity, suitable for header constants or static data members; it is not equivalent to "one copy per translation unit".

**What does `extern "C"` do, and not do?**

- **[Language Standard]** Language linkage affects linking semantics such as function types and the names of functions with external linkage, used to interface with C linkage interfaces.
- It does not turn the function body into C, does not disable exceptions, construction/destruction, overloading, or other C++ semantics, and does not automatically guarantee that any arbitrary C++ class, reference, exception, or STL type can cross a C ABI.
- **[Platform/ABI]** Actual symbol spelling, calling convention, structure layout, and C/C++ interoperability still depend on the platform ABI and compilers on both ends. Stable boundaries typically use C-compatible scalars, explicitly laid-out data, and opaque handles.
- C++ exceptions should not be allowed to cross a C call boundary that doesn't understand the exception ABI; they should be caught within the boundary and converted to error codes or explicit state.

### Follow-Up Questions

1. When the target is x86-64, can you directly assert that all object pointers and function pointers are 8 bytes? Which ABI or compilation results should be checked?
2. Why can't the form `sizeof(int&)` prove that references don't occupy object layout space? How do you verify reference members?
3. What are the effects of `const int*`, `int* const`, and top-level `const` in function parameters on overloading respectively?
4. What are the lifetime risks when returning `const std::string&` pointing at a local variable, a temporary, and a member object respectively?
5. Why are `std::string_view` parameters usually efficient, and what must be confirmed before storing one as a member?
6. Do block scope, automatic storage duration, and no linkage always appear together? Give a counterexample with function-local static.
7. Two translation units include the same header — why does the include guard still not prevent multiple definitions of an ordinary function?
8. Why can an inline function affected by different macros in two translation units link successfully yet still violate ODR?
9. Why shouldn't `extern "C"` APIs directly expose `std::string`, exceptions, or objects with virtual functions?

### Common Misconceptions

- Fixedly answering "32-bit pointers are 4 bytes, 64-bit pointers are 8 bytes" without distinguishing object pointers, function pointers, target ABI, and special address spaces
- Using `sizeof(ref)` to derive "references are always zero-cost and occupy no storage", ignoring reference members, cross-call boundaries, and ABI
- Treating null, wild, and dangling pointers as the same concept, and relying only on `p = nullptr` to solve all alias lifetime problems
- Claiming C++ has "pass by reference" and then no longer analyzing the borrow lifetime of references or views
- Conflating scope, storage duration, lifetime, and linkage into "locals are on the stack, globals are outside the heap"
- Believing include guards solve cross-translation-unit ODR
- Treating `inline` as a performance command and inline variables as one variable per file
- Believing `extern "C"` automatically provides a complete C++ ABI across compilers and versions

### Identity Difficulty

- **Intern/Campus hire**: Can distinguish pointers, references, `const` combinations, null/wild/dangling pointers, and the four storage durations; knows pointer size is platform-dependent.
- **Junior/intermediate C++ developer**: Can explain view and temporary object lifetime, scope/storage/linkage differences, header ODR, function-local static, and C ABI boundaries.
- **Senior/staff C++ developer**: Can review cross-translation-unit ODR, TLS shutdown, inline variable and ABI exposure risks, and verify implementation conclusions with target triples, symbols, layout dumps, or disassembly.

## 2. Object Model and Object-Oriented Programming

### Basic Questions and Answer Points

#### `struct` in C vs C++, `struct` vs `class` in C++

**What is the boundary between C's `struct` and C++ class types?**

- C and C++ are different languages; you cannot just answer "C++ structs have functions too". C++ class types can have constructors, destructors, member functions, access control, inheritance, virtual functions, templates, and more semantics.
- In C, tag names are in a different namespace from ordinary identifiers, so `struct Node` or `typedef` is often used; in C++, a class name can be used directly as a type name.
- The same source code may differ in initialization, implicit conversion, name lookup, and type compatibility between C and C++. Shared headers should be limited to a subset acceptable to both sides and verified by compiling each separately.
- **[Platform/ABI]** Even if fields look the same, cross-language binary interaction still requires agreeing on integer widths, alignment, packing, endianness, and calling conventions.

**What are the differences between `struct` and `class` in C++?**

- **[Language Standard]** The two are essentially equivalent in capability; `struct` defaults member access and base-class access to `public`, while `class` defaults to `private`.
- "structs can only hold data, classes must have methods" is wrong. Engineering commonly uses structs for simple value types and classes to emphasize invariants, but this is convention, not a language restriction.
- Access control is compile-time semantics, not a security boundary, and does not necessarily change the object's physical layout.

#### `union`, Alignment, Padding, and Type Properties

**How to answer about union active members and type punning?**

- **[Language Standard]** A union's non-static data members share storage; at any given time, usually only one member's lifetime is active.
- Reading a non-active member generally cannot serve as portable type punning; the common initial sequence of a standard-layout union has a restricted exception, but this cannot be generalized to arbitrary reinterpretation.
- C++20 offers `std::bit_cast` for constrained bit-level conversions; across versions, `std::memcpy` with trivially copyable types can be used. Dereferencing after `reinterpret_cast` must also satisfy lifetime, alignment, and aliasing.
- A union containing non-trivial members must explicitly manage construction and destruction; in practice, `std::variant` is usually preferred for expressing tagged sum types.

**Who determines alignment and padding?**

- **[Language Standard]** `alignof(T)` gives the type's alignment requirement; `sizeof(T)` includes padding needed to align array elements correctly. Before C++23, for non-zero-size non-variant non-static data members with the same access control, later-declared members have higher addresses; ordering guarantees between different access-control sections are weaker — you cannot broadly claim all field addresses increase in declaration order.
- **[Language Standard, since C++23]** Non-zero-size non-variant non-static data members have higher addresses in declaration order, no longer premised on the same access control; but members declared `[[no_unique_address]]` are potentially-overlapping subobjects and may share addresses with other objects — the strictly-increasing address conclusion cannot be extended to them.
- **[Platform/ABI]** Fundamental type sizes, natural alignment, tail padding utilization, bit-field allocation, and base subobject layout are further specified by the target ABI.
- `alignas` can request stricter effective alignment; over-aligned dynamic objects need matching aligned allocation support. Manually casting an arbitrary byte address to `T*` does not automatically satisfy alignment.
- `#pragma pack`, compiler attributes, and layout dumps are implementation tools, not portable C++ standard protocols. Changing packing may produce unaligned access costs or faults.

**What do standard-layout and trivially copyable each solve?**

- standard-layout constrains certain layout properties, applicable to some C interoperability, `offsetof`, and common initial sequence scenarios; it does not guarantee a complete wire format across different ABIs.
- trivially copyable allows object representation to be round-tripped via character/byte arrays or `memcpy`; it does not mean byte order, padding values, and cross-version format are stable.
- Polymorphic classes are usually not standard-layout. A type whose "fields are all POD-style" is not directly serializable or sendable over the network.
- In interviews, check layout property, lifetime, aliasing, endianness, and protocol compatibility separately — do not use the term "POD" to cover everything.

#### Object Lifetime, Construction/Destruction, and Special Members

**When does an object's lifetime begin and end?**

- **[Language Standard]** Available storage does not mean an object's lifetime has begun. An object's lifetime usually begins after obtaining suitable storage and completing the corresponding initialization, and ends when the destructor begins or the storage is reused/freed under other rules.
- Accessing an object outside its lifetime through a glvalue is typically undefined behavior; a few operations and implicit-lifetime types have special rules — do not treat "the bytes are still in memory" as the object still existing.
- When a constructor throws, the complete object was not successfully constructed and its destructor does not run; base and member subobjects that completed construction are destroyed per rules, so resources should go into member RAII types.
- Destruction order is roughly the reverse of construction: the most-derived destructor body runs first, then members and bases are destroyed; array elements are destroyed in reverse order. The order of static objects across translation units needs additional control.

**When does the compiler implicitly declare or delete copy/move operations?**

- Special member functions include the default constructor, destructor, copy/move constructor, and copy/move assignment.
- User-declaring certain copy, move, or destructor functions suppresses or affects the implicit generation of other special members; when a member or base doesn't support the corresponding operation, the function may be defined as deleted.
- `= default` requests the compiler to generate semantics; `= delete` forbids calls; whether it is trivial, `constexpr`, or `noexcept` also depends on members, bases, and the standard version.
- Do not just memorize the mantra "declare a destructor and you lose move" — let compiler traits, explicit default/delete, and tests express the type's contract.

#### Virtual Functions, Virtual Destructors, and Dynamic Dispatch

**Are virtual functions always called through a vtable?**

- **[Language Standard]** The standard specifies the observable semantics of virtual dispatch and does not require the existence, count, location, or fixed memory layout of vtables or vptrs.
- **[Platform/ABI]** Mainstream C++ ABIs usually use vtable/vptr, and may generate pointer adjustment thunks for multiple inheritance and store extra offset information for virtual inheritance; specific layouts must be bound to the Itanium C++ ABI, MSVC ABI, etc.
- **[Compiler/Standard Library Implementation]** Compilers can devirtualize when the dynamic type is provable, calling directly or inlining; this does not change the virtual semantics at the source level.
- Virtual calls during constructor/destructor are treated according to the class of the current construction or destruction phase and will not dispatch to not-yet-constructed or already-destroyed more-derived parts.

**When must a base destructor be virtual?**

- For a polymorphic base allowing owning deletion, a virtual destructor should be the default; on a normal deletion path, deleting an actual derived object through a non-virtual base pointer is undefined behavior.
- **[Language Standard, since C++20]** Destroying delete provides a controlled exception path: if a destroying `operator delete` is found and selected, that function is responsible for completing destruction and deallocation per the real object's contract. The rules cannot be simplified to "any non-virtual base destructor takes the same path", nor can it be assumed that destroying delete automatically recognizes the dynamic type.
- The safe recommendation remains: polymorphic base owning deletion uses a virtual destructor by default; only a controlled destroying delete/ownership design that can explicitly prove dynamic type determination, complete destruction, matched deallocation, and module lifecycle should consider a non-virtual scheme.
- When used only as a non-owning interface with deletion through the base forbidden, a protected non-virtual destructor can express the constraint; the ownership API must be consistent with this.
- A virtual destructor makes the type polymorphic and usually has ABI/layout impact; this is not a reason to refuse necessary correctness, nor should virtual destructors be indiscriminately added to all value types.
- `override` should be applied to overriding functions so the compiler checks signatures; `final` can restrict further overriding or inheritance and may help optimization, but its primary purpose is expressing design.

**What are the core risks of multiple inheritance and virtual inheritance?**

- A non-virtual diamond contains multiple copies of the common base subobject; virtual inheritance lets the most-derived object share one virtual base, constructed by the most-derived constructor.
- When a pointer adjusts from derived to different bases, its address may change; `reinterpret_cast` cannot replace correct `static_cast`/`dynamic_cast` adjustment.
- `dynamic_cast` provides runtime checking for polymorphic hierarchies; pointer failure returns null, reference failure throws `std::bad_cast`. RTTI cost and implementation are ABI/compiler scope.
- Multiple inheritance is not inherently wrong, but cross-shared-library ABI, object size, construction order, and ownership interfaces become more complex. Composition is usually easier to maintain.

#### Object Slicing, Covariance, and ABI Stability

**What is object slicing?**

- Assigning a derived object by value to a base object copies only the base subobject, slicing off derived state and dynamic type; later calling virtual functions through that base value will not restore the original derived object.
- Polymorphic objects should be passed via references, pointers, or explicit type-erasure/value-polymorphism wrappers; a container `std::vector<Base>` cannot hold heterogeneous derived values while preserving their original dynamic types.
- Covariant return of virtual functions only applies to pointers/references to class types satisfying the rules, not to arbitrary smart pointers.

**Why is "same compiler means stable ABI" still insufficient?**

- **[Platform/ABI]** ABI is also affected by compiler version/flags, standard library ABI, exception/RTTI switches, packing, visibility, LTO, CPU features, and build mode.
- Exposing STL containers, inline private layouts, or polymorphic classes in a public ABI couples the standard library implementation and object layout to callers.
- Stable plugin boundaries more commonly use versioned C ABI, opaque handles, explicit ownership, and capability negotiation; C++ internals can still use classes and RAII.

10. When exposing `std::string` and a virtual class across a dynamic library interface, which ABI dimensions need review?

### Common Misconceptions

- Only answering "struct defaults to public, class defaults to private", completely ignoring that C and C++ are different languages and cross-language ABI
- Doing arbitrary type punning with unions or `reinterpret_cast` without checking active member, lifetime, alignment, and aliasing
- Conflating standard-layout, trivially copyable, POD, and serializable wire format
- Not distinguishing member address ordering before/after C++23, or ignoring that `[[no_unique_address]]` potentially-overlapping members can share addresses
- Believing old bytes in storage mean the old object's lifetime is still active
- Stating vtable/vptr count and position as guaranteed by the C++ standard
- Believing virtual calls in constructors can access complete derived state
- Forgetting the deletion contract of polymorphic bases; or seeing C++20 destroying delete and mistakenly assuming any non-virtual base deletion will automatically destruct correctly
- Describing virtual inheritance as "just saving one copy of memory" without explaining construction ownership and pointer adjustment
- Mistakenly assuming the same compiler family is naturally ABI compatible

- **Junior/intermediate C++ developer**: Can explain standard-layout/trivially copyable, object slicing, constructor exceptions, multiple inheritance adjustment, and object lifetime.
- **Senior/staff C++ developer**: Can rigorously distinguish virtual semantics from vtable ABI, design stable shared-library boundaries, and review ABI with layout dump, symbol, RTTI, and disassembly evidence.

## 3. RAII, Resource Management, and Exception Safety

### Basic Questions and Answer Points

#### RAII and Ownership

**Is RAII only for managing memory?**

- RAII binds resource acquisition to object initialization and puts release in the destructor, so normal return, early return, and exception unwinding share the same cleanup path.
- Resources include memory, file descriptors, sockets, mutexes, transaction guards, temporary files, mapped regions, and callback registrations — not limited to `new`/`delete`.
- RAII types must clearly define ownership, move/copy semantics, and the destructor's failure strategy. Writing only `delete` in the destructor but allowing erroneous copies still causes double free.
- Resource handles often have a legitimate invalid state; constructor failure should not produce a half-initialized owner, and after a move the source should remain in a destructible, assignable valid state.

**Must raw pointers never appear?**

- Raw pointers and references are suitable for expressing non-owning observation; the problem is not "rawness" itself, but whether ownership and lifetime are clear.
- Owning raw pointers easily leak under early returns, exceptions, and complex aliasing — they should be encapsulated in RAII owners.
- APIs should not guess transfer from `T*`; use `std::unique_ptr<T>`, factory return values, span/view, or clearly named handles to express the contract.

#### Rule of Zero, Rule of Five, and Copy/Move

**Why is Rule of Zero preferred over Rule of Five?**

- Rule of Zero: have members use correct RAII types so compiler-generated destructor/copy/move naturally compose; business classes don't directly manage raw resources.
- If a class directly owns non-trivially-manageable resources and needs custom lifecycle, you generally need to review destructor, copy/move constructor, copy/move assignment as a whole — Rule of Five.
- When a resource can only be exclusively owned, delete copy and provide move; when copyable, define deep copy, shared ownership, or copy-on-write semantics explicitly.
- Copy-and-swap can provide a clear strong guarantee, but incurs extra temporary objects and resource peaks; it is not the only elegant implementation of every assignment.

**Does move equal "zero-copy"?**

- **[Language Standard]** Move is just the mechanism of calling the appropriate overload for an rvalue; the specific type may transfer a handle, move element-by-element, or even degrade to a copy.
- Standard library objects after being moved are usually in a valid but unspecified state and can only perform operations their contract allows; do not assume they are necessarily empty.
- `std::move` itself only performs a cast and moves no bytes. Using `std::move` on a `const T` often cannot invoke a move constructor requiring `T&&` and may fall back to a copy.
- Some standard containers choose move or copy during reallocation based on conditions like whether the element move is `noexcept` and whether it is copyable, to maintain exception guarantees; this is the combined effect of contract conditions and implementation strategy — it cannot be summarized as "always move".

#### Exception Safety Guarantees

**What are the no-throw, strong, and basic guarantees?**

- No-throw guarantee: the operation promises not to throw and to complete its contract; common in destructors, swap, and move primitives; a `noexcept` violation calls `std::terminate`.
- Strong guarantee: on failure, the observable state is as if the operation never happened, typically by constructing a temporary result first then commit/swap.
- Basic guarantee: on failure, invariants still hold and no resources leak, but values may have changed.
- No guarantee means not even basic invariants can be relied upon after an exception. Interface documentation and code review should specify which level is required rather than vaguely saying "exception safe".

**Can destructors throw?**

- Destructors should generally be non-throwing; letting a destructor escape an exception during stack unwinding with an active exception triggers `std::terminate`.
- If release failure must be reported, provide explicit `close`/`commit` operations so the caller can handle errors; destructors do best-effort cleanup or record non-throwing diagnostics.
- The default destructor's exception specification is affected by members/bases. Explicitly writing `noexcept(false)` is rarely a good interface for a resource owner.

#### `unique_ptr`

**What are the ownership and deleter details of `unique_ptr`?**

- `std::unique_ptr<T, D>` expresses exclusive ownership, is non-copyable and movable, and releases through the deleter when going out of scope.
- The deleter is part of the type and can hold a file descriptor closer, C API release function, or allocator context. Stateful deleters may increase the `unique_ptr` size; empty deleters are often compressed away, but layout is implementation-defined.
- `unique_ptr<T[]>` uses array deletion semantics and provides subscripting; you cannot use `unique_ptr<T>` to manage `new T[]`.
- `release()` only gives up ownership and returns the pointer without freeing; `reset()` frees the old resource and takes over a new pointer.
- Incomplete types can work with `unique_ptr` for pImpl, but the location executing the default deleter must see the complete type; usually the owning class destructor is defined in the implementation file.

#### `shared_ptr`, `weak_ptr`, and the Control Block

**What does `shared_ptr` typically contain, and what does the control block do?**

- **[Language Standard]** `shared_ptr` provides shared ownership semantics. Multiple handles destroy the managed object when the last owning reference disappears; weak ownership does not extend the managed object's lifetime.
- **[Compiler/Standard Library Implementation]** Mainstream implementations typically have the handle store a stored pointer and a control-block pointer; the control block stores strong/weak counts, deleter, allocator, etc.; the standard does not specify field layout or count widths.
- `std::make_shared` can typically place the object and control block in one allocation, improving locality and exception safety; this is a permitted and common implementation strategy, not a language-level physical commitment that "any implementation always allocates only once".
- When the strong count reaches zero the object is destroyed; while `weak_ptr`s remain, the control block may persist. The make_shared combined allocation may therefore retain the whole block of storage even though the object's lifetime has ended.
- The aliasing constructor can share one control block while the stored pointer points to a related subobject; "same/different `get()`" alone cannot determine the ownership group.

**What exactly does `shared_ptr` thread safety guarantee?**

- **[Language Standard]** Different `shared_ptr` objects, even sharing ownership, can have handle-level operations performed by different threads without data races from control block counting.
- The same `shared_ptr` object having non-const handle mutations performed by multiple threads still needs synchronization; C++20 offers `std::atomic<std::shared_ptr<T>>`.
- Control block reference count safety does not mean the pointee is thread-safe. Multiple threads modifying the same `T` through their own `shared_ptr<T>` must still lock or otherwise synchronize per `T`'s invariants.
- `use_count()` is only an instantaneous observation and cannot serve as a reliable check-then-act condition for "I'm the only owner, so no synchronization needed".

**How do reference cycles occur, and how does `weak_ptr` solve them?**

- If a cycle forms in the ownership graph consisting entirely of strong edges, strong counts remain non-zero after external handles disappear and objects will not be destroyed.
- Changing semantically non-owning, parent/back-reference, observer, or cache edges to `weak_ptr` breaks ownership cycles.
- `weak_ptr::lock()` atomically attempts to obtain temporary shared ownership, returning an empty `shared_ptr` on failure; checking `expired()` first then using it has a TOCTOU — check the `lock()` result directly.
- `enable_shared_from_this` relies on the object already being established by suitable `shared_ptr` ownership; calling `shared_from_this()` in a constructor or creating multiple independent control blocks for the same raw pointer are serious errors.

#### Custom Deleters and Cross-Module Release

**Why are custom deleters often needed across dynamic library boundaries?**

- **[Platform/ABI]** Allocation and deallocation may need to happen under the same runtime, heap, allocator instance, or module contract. The caller directly `delete`-ing an object allocated by another module's specific factory may be incompatible.
- A factory can return a unique/shared owner with a module-provided deleter, or provide a paired `create/destroy` C ABI.
- The deleter must also match the resource kind: `fclose`, `closedir`, `munmap`, `SSL_free`, custom pool releases cannot be replaced by plain `delete`.
- The code and allocator context in the deleter must outlive the last owner; early unloading of a dynamic library invalidates function pointers.

## 4. STL, Templates, and Modern C++

### Basic Questions and Answer Points

#### `vector` Complexity, Capacity, and Invalidation Rules

**How does `vector` grow, and what is the growth factor?**

- **[Language Standard]** Except for the `std::vector<bool>` specialization, `vector<T>` provides contiguous storage with amortized constant complexity for end insertion; the standard does not specify a fixed capacity growth factor.
- **[Language Standard]** `std::vector<bool>` is a space-optimized specialization where element access uses proxy references, not representing a contiguous run of bool objects; the `T*`, real `bool&`, or contiguous range intuitions of ordinary `vector<T>` do not apply.
- **[Compiler/Standard Library Implementation]** 1.5×, 2×, or strategies related to requested capacity/element size are implementation choices that may vary with standard library version, debug mode, and allocator.
- On reallocation, all references, pointers, and iterators are invalidated; `push_back`/`emplace_back` without reallocation generally preserves existing elements' references/iterators, but the old `end()` is invalidated.
- Inserting in the middle without reallocation invalidates iterators/references at and after the insertion point; erase invalidates iterators/references at and after the erased position.
- `reserve(n)` only guarantees capacity reaches at least the request and avoids growth reallocation while not exceeding capacity, without changing size; `resize(n)` changes the element count, constructing/destroying elements.

**Does `shrink_to_fit()` guarantee returning memory?**

- **[Language Standard]** It is a non-binding request; you cannot rely on it to guarantee capacity becomes size or RSS drops.
- **[OS/allocator]** Even if the container frees the allocation, the allocator may keep the arena/cache in the process without immediately returning it to the OS.
- To prove memory improvement, look at container capacity, heap allocation profile, allocator stats, RSS/PSS, and working set together — not just one.

#### `deque`, `list`, `map`, and `unordered_map`

**How to compare common containers?**

- `deque` supports random access with typically constant-complexity insertion/removal at both ends, but does not require the whole range to be contiguous; middle insertion movement cost is usually linear.
- **[Language Standard]** `std::list`'s standard contract is a sequence container with bidirectional iterators, constant-time single-element insertion/erase at known positions, and iterator/reference stability except for erased elements; range insertion/erase complexity grows with the number of elements processed. The standard does not specify node fields, pointer counts, or allocation granularity.
- **[Compiler/Standard Library Implementation]** Mainstream standard library implementations usually use doubly-linked nodes, commonly with per-node allocation, extra pointer overhead, and poor locality; these are implementation characteristics to measure during selection, not physical layouts required by the standard.
- `map`/`set` provide associative semantics ordered by strict weak ordering with typically logarithmic find/insert/erase; "must be a red-black tree" is a mainstream implementation, not a standard requirement.
- `unordered_map`/`unordered_set` provide average constant, worst-case linear find/insert/erase complexity; hash quality, load factor, adversarial keys, and rehash determine actual behavior.
- Do not select containers by Big-O alone. Element count, cache locality, allocation, iteration pattern, stable addresses, ordering needs, and attack surface are equally important.

**How to answer reliably about iterator invalidation?**

- Node-based ordered containers: insert generally does not invalidate existing iterators/references; erase only invalidates the erased elements; node handle operations have separate contracts.
- Unordered containers: rehash invalidates iterators, but element references/pointers generally remain valid; erase invalidates only handles related to erased elements.
- `deque` has fine-grained rules for different insert/erase positions: end insertion, middle insertion, and end removal affect iterators/references differently. You cannot summarize with "deque never invalidates" — check the target standard's contract for the specific operation.
- `end()` is also an iterator and often needs to be re-obtained after size changes. Debug iterators can report earlier but are not a safety mechanism in release builds.

#### Algorithms, Ranges, and Complexity Contracts

**Is STL complexity a performance guarantee?**

- Complexity is an upper bound or amortized constraint on abstract operation counts, not equal to wall-clock latency, allocation counts, cache misses, or syscall counts.
- Comparators/hashes must satisfy corresponding semantics; violating strict weak ordering breaks the premises of ordered algorithms/containers — the result is not "slightly wrong ordering".
- C++20 ranges improve composability through iterator/sentinel, views, and constraints; many views are non-owning and lazy — when the underlying range is invalidated, the view also dangles.
- Parallel algorithms are additionally constrained by execution policies, implementation support, and callable side effects; specifying a policy does not guarantee parallelism or speed.

#### Allocators, Raw Storage, and Object Lifetime

**Do allocators allocate objects or storage?**

- **[Language Standard]** The allocator abstraction is responsible for obtaining suitable raw storage; object construction/destruction are separate lifetime operations. Modern code typically uses `std::allocator_traits`, `std::construct_at` (C++20), and `std::destroy_at`.
- Container allocators also involve whether allocation propagates on copy/move/swap, allocator equality, and the constraint that deallocation must return to a compatible allocator.
- `std::pmr` (C++17) makes memory resources runtime-polymorphic, suitable for arenas, request-scoped allocation, and bulk release; containers must not outlive their `memory_resource`.
- A monotonic resource's single deallocate typically does not reclaim individual blocks; its advantage comes from bulk lifetimes; it is unsuitable for unboundedly growing long-lived objects without a reset boundary.

**What do placement new and `std::launder` each solve?**

- Placement new begins construction of a new object in caller-provided suitable storage, itself not allocating backing storage; on failure the backing storage remains the caller's responsibility.
- The new object must satisfy size/alignment; old non-trivial objects usually must be properly destroyed first; ultimately you cannot use ordinary `delete` on the placement object unless the storage truly came from a matching new-expression and the contract allows it.
- **[Language Standard, since C++17]** `std::launder` is used in specific scenarios to obtain a usable pointer to a new object, e.g., when replacement involves const/complete objects, base subobjects, etc. that prevent the old pointer from transparently redirecting.
- `launder` is not a tool for "making arbitrary type punning legal", nor does it fix alignment, strict aliasing, or nonexistent lifetimes.

#### `auto`, `decltype`, Value Categories, and Forwarding

**What is the deduction difference between `auto` and `decltype`?**

- `auto` largely uses template argument deduction rules, typically stripping top-level cv/ref in by-value form; `auto&`, `const auto&`, `auto&&` express different constraints respectively.
- `decltype(expr)` has special rules for unparenthesized id-expressions/member access; other expressions deduce `T&`, `T&&`, or `T` based on value category. `decltype((x))` on an lvalue `x` yields a reference type.
- `decltype(auto)` preserves `decltype` rules; returning a local variable with an extra set of parentheses may unexpectedly return a dangling reference.
- `auto` is not "dynamic type" — the type is still determined at compile time.

**What are the boundaries of rvalue references, move semantics, and perfect forwarding?**

- A named variable of type `T&&` is still an lvalue expression; to forward again in its original value category, use `std::move` or `std::forward`.
- A forwarding reference only appears in the specific `T&&` form where deduction occurs; a fixed-type `Widget&&` in a class is not a forwarding reference.
- Reference collapsing merges `T& &`, `T& &&`, `T&& &` into `T&`, with only `T&& &&` becoming `T&&`.
- Perfect forwarding preserves value category and cv/ref, but may also amplify overload, initializer-list, bit-field, and lifetime problems; do not write every wrapper as an unconstrained universal reference.

#### Lambdas, `constexpr`, SFINAE, Concepts, and Coroutines

**Where do lambda captures most commonly go wrong?**

- `[=]`/`[&]` capture semantics do not equal automatic safety. Reference captures for async execution or capturing `this` may dangle before the closure is invoked.
- Capturing a `shared_ptr` can extend object lifetime but may also form cycles; capturing a `weak_ptr` and locking at execution time is often better for callback registration.
- Generalized lambda capture (C++14) can move-capture unique resources; the closure type's copy/move capability is determined by its captures.
- Concurrent invocation of the same mutable closure still requires synchronizing its captured state.

**Does `constexpr` mean it definitely executes at compile time?**

- `constexpr` means the entity can participate in constant evaluation and satisfy the corresponding restrictions; calling a `constexpr` function on a non-constant-expression can still execute at runtime.
- `consteval` (C++20) requires immediate invocations to be evaluated at compile time; `constinit` (C++20) constrains static/thread storage variable initialization without making the variable automatically const.
- Compile-time computation shifts some cost to build time and binary; whether it's faster still requires considering code size and runtime paths.

**How should SFINAE, concepts, and coroutines be layered?**

- SFINAE removes candidates from the overload set when template substitution fails in the immediate context; it is not a general exception mechanism for all errors in the template body.
- `if constexpr` (C++17) discards non-selected branches at instantiation, suitable for local compile-time branching, but syntax outside the condition must still be valid.
- Concepts/constraints (C++20) participate in overload ordering with named semantic constraints, generally more readable than deep `enable_if`; they constrain valid expressions but do not automatically prove business semantics.
- Coroutines (C++20) are transformed by the compiler into state machines with promise/frames. They are not OS threads and do not come with a scheduler, I/O runtime, cancellation, or backpressure.
- **[Compiler/Standard Library Implementation]** Whether the coroutine frame is placed on the caller, heap, or elided depends on lifetime, optimization, and implementation; you cannot fixedly answer "coroutine objects always heap-allocate once".

### Common Misconceptions

## 5. Memory Management and System Interaction

### Basic Questions and Answer Points

#### `new`/`delete` vs `malloc`/`free`

**What are the semantic differences between the two API families?**

- **[Language Standard]** A new-expression first obtains storage, then constructs the object, and returns a typed pointer; ordinary failure throws `std::bad_alloc` by default, while the `std::nothrow` form returns null on failure.
- **[Language Standard]** An ordinary delete-expression selecting a non-destroying deallocation function first calls the destructor, then calls the matching deallocation function; `delete nullptr` is safe and has no effect.
- **[Language Standard, since C++20]** If deallocation function lookup selects a destroying `operator delete`, the delete-expression no longer separately calls the destructor first; that function is responsible for correct destruction and storage release. Implementing this interface must explicitly handle the complete object lifecycle — it cannot be treated as an ordinary deallocation callback.
- `malloc` allocates raw storage satisfying fundamental alignment requirements, returns `void*`, and returns null on failure; it does not universally guarantee extra alignment for over-aligned types, nor does it call constructors. `free` does not call destructors.
- C++17 over-aligned types may use aligned `operator new/delete` overloads; custom class-specific allocation functions can also participate. A new-expression is not equivalent to a fixed call to libc `malloc`.
- `new T[n]` must be matched with `delete[]`, and `malloc/calloc/realloc` must be matched with `free`. Mixing allocation/deallocation families is undefined behavior.

**Why can't `realloc` universally replace C++ object moves?**

- `realloc` operates on raw allocations, potentially moving bytes and freeing the old block; it knows nothing about non-trivial objects' constructors, destructors, self-pointers, and invariants.
- Directly `realloc`-ing arrays of general C++ objects destroys lifetime and object semantics. Containers must construct/move elements to new storage per element traits, then destroy old elements.
- For trivially copyable/implicit-lifetime types, low-level storage still must satisfy the corresponding standard version's lifetime and API premises — do not judge solely by "it looks like a struct".

#### Alignment, Placement Construction, and Aliasing

**What must a hand-written memory pool guarantee at minimum?**

- Returned addresses satisfy the requested type's alignment; block sizes, headers, and free-list pointers must not break alignment.
- Allocation only provides storage; object lifetime must begin at the correct point; non-trivial object lifetime must end before release.
- The pool itself must outlive all objects allocated from it and define thread-safety, cross-thread free, and shutdown behavior.
- Handle size classes, large allocations, exception rollback, double free, use-after-free, poisoning, and debug instrumentation.
- If relying on `reinterpret_cast` or freelist overlay, review aliasing, active lifetime, and pointer provenance; "runs at the current optimization level" is not evidence of standard correctness.

**How to understand strict aliasing and character access?**

- **[Language Standard]** Accessing an object through a disallowed glvalue type can produce undefined behavior and allow the optimizer to make seemingly counterintuitive transformations.
- `char`, `unsigned char`, and `std::byte` can be used to inspect object representation, but treating arbitrary bytes as an existing complex `T` still requires satisfying lifetime, alignment, and representation.
- `memcpy`/`bit_cast` are bit-copy tools; they do not automatically validate that the input representation is valid for the target type; trap/invalid representations and padding still need consideration.

#### Memory Pools, Fragmentation, and Alternative Allocators

**What are internal and external fragmentation?**

- Internal fragmentation is wasted space inside an allocated block or size class larger than the request; alignment and metadata also add overhead.
- External fragmentation is when total free space is sufficient but scattered, making it hard to satisfy large contiguous requests; observe separately at virtual address, page, arena, and physical residency levels.
- Pools/arenas can reduce general-purpose allocator overhead by unifying size/lifetime, but may increase peaks, delayed returns, and cross-request memory retention.
- Before optimizing, measure allocation rate, size distribution, lifetime distribution, contention, RSS/PSS, page faults, and tail latency.

**What scenarios suit jemalloc/tcmalloc?**

- **[OS/allocator]** They are specific allocator implementations, often reducing contention via thread/per-CPU caches, size classes, and multiple arenas, while providing profiling/tuning capabilities.
- Costs may include cache retention, fragmentation, RSS deviating from live bytes, cross-thread free behavior, and operational complexity.
- Do not switch allocators just because of "high concurrency". Compare throughput, P99, CPU, RSS, faults, and release behavior under the same workload, sampling, and warm-up conditions.
- Allocator replacement must also check static/dynamic linking, sanitizer interposition, fork, huge pages, container memory limits, and third-party library compatibility.

#### `brk`, `mmap`, Virtual Memory, and RSS

**Do large `malloc`s always go through `mmap` and small ones through `brk`?**

- No — this is not a C++ specification. **[OS/allocator]** Some glibc allocator versions combine size, dynamic thresholds, arenas, historical requests, and tunables to choose heap growth or anonymous mapping; fixed thresholds are not cross-version contracts.
- Other libcs or allocators can differ entirely; macOS, Windows, and Linux virtual memory APIs also differ.
- Even from `mmap`, pages are typically established on demand for physical residency; virtual size, committed memory, RSS, PSS, dirty pages, and cgroup charges are not the same metric.
- RSS not dropping immediately after `free` may be due to arena/cache retention, pages not meeting return conditions, fragmentation, or kernel accounting timing; you cannot directly assert a memory leak.

**How do page faults and copy-on-write affect services?**

- First touch of demand-paged memory can cause minor faults; I/O or swap involvement can cause major faults with completely different latency characteristics.
- After `fork`, pages are typically copy-on-write; writes by either parent or child create private copies. Large processes writing allocator/GC hot spots after fork can cause significant RSS peaks.
- Transparent Huge Pages, NUMA placement, page cache, and memory reclaim all affect tail latency — these are OS and deployment environment issues, not C++ object model issues.

#### Leaks, Out-of-Bounds, and Use-After-Free

**How to first classify "process memory keeps growing"?**

- Still-reachable retention: ownership graphs, unbounded caches/queues, or long-lived owners still hold objects; use heap profilers, allocator profiles, capacity metrics, and reference chain analysis. LSan by default does not report still-reachable objects as primary leaks.
- Unreachable allocations from lost owners: use LSan or Memcheck to correlate allocation stacks; LSan by default mainly reports unreachable allocations and cannot rule out still-reachable retention.
- Allocator retention/fragmentation: live bytes stable but reserved/RSS high; needs allocator stats and size/lifetime distribution.
- Non-heap memory: thread stacks, mmap, shared memory, JIT/code, page cache, driver buffers, etc.
- Unbounded workload caches or queues: semantically still reachable; check capacity metrics and heap/allocator profiles rather than waiting for LSan to report unreachable leaks.
- First establish metric definitions and a timeline, then decide whether it's a code leak, capacity bug, allocator behavior, or OS accounting.

### Common Misconceptions

## 6. Concurrency, Atomics, and the Memory Model

### Basic Questions and Answer Points

#### `thread`, Mutexes, and Lock Design

**What should be noted about `std::thread` lifecycle?**

- If a joinable `std::thread` is still not `join`ed/`detach`ed when its destructor runs, it calls `std::terminate`; the owner must define an ending protocol.
- `detach` is not automatic resource management. A detached task may still access destroyed objects, lose errors, delay process exit, or continue holding resources.
- C++20 `std::jthread`'s destructor requests stop and joins, providing cooperative cancellation with `stop_token`; blocking APIs must still actually respond to cancellation.
- When a thread function captures references, the referents must outlive the thread's completion; `std::ref` only changes parameter wrapping, not lifetime.

**Should a mutex protect data or invariants?**

- A mutex should protect invariants spanning multiple fields and operations, with clear lock ownership; saying "lock this variable" often misses check-then-act.
- Use `std::lock_guard`, `std::unique_lock`, `std::scoped_lock` so unlock goes through RAII; for multiple locks, use a uniform order or deadlock-avoidance primitive.
- Do not hold locks while executing unknown callbacks, long I/O, or potentially re-entrant code; if needed, copy the state first, release the lock, then perform external operations.
- `std::shared_mutex` being read-heavy does not mean it's necessarily faster; reader/writer strategy, starvation, and overhead depend on the implementation — profile.

#### Condition Variables, Futures, and Promises

**Why must condition variables be used with a predicate loop?**

- Wait can have spurious wakeups; even when woken by a notify, another thread may have modified the condition first.
- The correct form is checking the predicate under the lock and waiting if unmet; `wait(lock, pred)` encapsulates the loop.
- Modifying the shared state underlying the predicate is usually done under the same mutex before notifying. Notify itself does not store "event counts" — notify-then-wait can lose one-shot signal designs.
- Timeouts should use the predicate overload and distinguish deadline from a single wake; repeatedly using relative timeouts in a loop can extend total wait due to multiple wakes.

**What do future/promise solve?**

- A promise sets a value or exception; a future retrieves the result and establishes corresponding synchronization; an ordinary future can typically only `get` once, while `shared_future` allows multiple shared reads.
- A broken promise gives the future an exception state instead of waiting silently forever.
- If `std::async`'s launch policy is unspecified, the implementation may choose async or deferred; when thread/execution semantics matter, specify the policy or use a controlled executor/thread pool.
- Futures do not automatically provide cancellation, backpressure, or bounded scheduling; production services usually also need task ownership and executor contracts.

#### Data Races, Happens-Before, and Publication

**Why is a data race not just "occasionally reading a stale value"?**

- **[Language Standard]** A data race forms when two potentially concurrent conflicting actions access the same memory location, at least one is not atomic, and neither happens before the other; program behavior is undefined.
- The compiler may reorder, eliminate, or coalesce accesses based on data-race-free assumptions, so the phenomenon is not solely determined by CPU caches.
- Happens-before is formed transitively through relations like sequenced-before and synchronizes-with; real-time thread ordering or `sleep` does not establish C++ memory model synchronization.
- Mutex unlock with subsequent successful lock, thread start/join, condition variables, atomic release/acquire, etc. can establish the specified relations, but each primitive's boundaries differ.

**How to safely publish an object?**

- After the producer completes ordinary writes, publish the pointer/flag with a release store; the consumer receives with an acquire load reading that value and can see writes sequenced before the release.
- If the consumer's acquire does not read a value from the corresponding release sequence, it cannot claim the object has been published.
- Mutex-protected queues, one-time initialization, and message passing are generally easier to review than hand-written atomic publication.
- `volatile` does not establish inter-thread synchronization; it is for specific observable side-effect scenarios and cannot replace atomic or mutex.

#### Atomics and Memory Order

**How to understand the six common memory orders?**

- `memory_order_relaxed` guarantees atomicity and modification order for that atomic object's operations, but establishes no cross-object release/acquire visibility.
- `memory_order_release` is for the publishing side of stores/RMW; `memory_order_acquire` is for the receiving side of loads/RMW; when the read relation is satisfied, synchronizes-with is established.
- `memory_order_acq_rel` is commonly used for RMWs that both read old values and publish new state.
- `memory_order_seq_cst` provides a single total order constraint for seq_cst operations in addition to acquire/release semantics; it does not automatically make non-atomic conflicting accesses safe.
- `memory_order_consume` has long had implementation and usage difficulties; mainstream implementations often treat it as acquire; interviews should not treat theoretical dependency ordering as an optimization to rely on casually.
- Memory order is part of the program's proof, not a "relaxed is faster" switch. Without complete invariants and litmus tests, prefer clearer locks or stronger ordering.

**What are the differences between CAS `weak`, `strong`, and failure order?**

- `compare_exchange_weak` may spuriously fail, suitable for retry loops that were going to loop anyway; `strong` disallows such spurious failures but still fails on value mismatch.
- On CAS failure, the actual value is written back into `expected`, so retry loops must recompute the desired state.
- The failure memory order cannot contain release semantics and cannot be stronger than the allowed range of the corresponding success order; interface design should review this explicitly.
- CAS loops under high contention may retry heavily, causing cache-line bouncing and tail latency; lock-free does not equal low cost.

#### ABA, Reclamation, and Progress Guarantees

**What is ABA?**

- CAS seeing a value go A → B → A mistakenly believes state hasn't changed; an identical pointer does not mean the logical node is the same generation.
- Tagged/versioned pointers can reduce pre-wrap ABA; hazard pointers, epoch-based reclamation, and reference counting solve different parts of node lifetime/reclamation.
- Solving ABA alone does not solve use-after-free; merely delaying free does not guarantee linearization correctness.
- Reclamation schemes need to handle stalled threads, thread exit, batching, memory pressure, and shutdown.

**What are the differences between lock-free, wait-free, and obstruction-free?**

- Lock-free generally guarantees the system as a whole makes continuous progress but does not guarantee any individual thread won't starve.
- Wait-free requires every operation to complete within a bounded number of steps, a stronger guarantee with higher implementation cost.
- Obstruction-free only guarantees a thread completes when it runs exclusively long enough.
- `atomic<T>::is_lock_free()` can be queried per-object/runtime; `is_always_lock_free` (C++17) gives a compile-time property; the standard does not guarantee all atomic types are implemented with lock-free CPU instructions.
- A lock-free algorithm does not mean the business is faster. A low-contention mutex may use less CPU, be fairer, and be easier to maintain.

#### False Sharing and Cache Coherence

**What is false sharing?**

- Different threads modifying logically independent data located in the same coherence unit cause cache lines to bounce between cores.
- **[Platform/ABI]** Cache line size, NUMA topology, and coherence behavior are hardware/platform attributes; 64 bytes cannot be treated as a C++ guarantee for all machines.
- C++17 provides `std::hardware_destructive_interference_size` and similar implementation-provided constants, but their availability and accuracy still need target standard library/platform verification.
- Padding may reduce false sharing but also increases footprint and reduces cache density; must be verified with hardware counters and workload.

## 7. Network Programming and High-Performance Services

### Basic Questions and Answer Points

#### Socket Lifecycle, Partial I/O, and RAII

**Does one `read`/`write` correspond to one complete message?**

- Stream sockets provide a byte stream that does not preserve application message boundaries; one read may return less than requested, merge multiple messages, or return EOF, and one write may also write only partially.
- Application protocols must define framing — e.g., fixed header + length, delimiter, or self-describing encoding — and handle coalescing, splitting, malformed lengths, and size limits.
- Non-blocking I/O's `EAGAIN`/`EWOULDBLOCK` means it cannot continue right now, not connection failure; `EINTR`, half-close, RST, and timeouts must be handled per operation semantics.
- File descriptors should be managed by move-only RAII owners with clear close, shutdown, dup, and ownership transfer semantics; after an integer fd is reused, old async events may incorrectly target new resources.

#### `epoll` and Reactor

**Does `epoll` provide readiness or completion?**

- **[OS/allocator]** Linux `epoll` reports file descriptor readiness/state changes; the application still performs actual read/write after receiving the event; ready does not guarantee one I/O completes the entire business request.
- Level-triggered mode reports repeatedly while conditions still hold; edge-triggered mode only reports edges and typically requires non-blocking with looping drain to `EAGAIN`, otherwise opportunities to continue processing may be lost.
- `EPOLLONESHOT` events need explicit rearm after firing, suitable for preventing one fd from being handled by multiple workers simultaneously, but the state machine is more complex.
- Error/hangup must be handled even if not explicitly requested in the event mask; races between close and fd reuse, cross-thread remove, and queued events need generation/ownership design.

**What are a Reactor's core responsibilities?**

- A Reactor organizes readiness demultiplexing, connection state machines, timers, accept/read/write, and callback dispatch.
- One-loop-per-thread, shared acceptor, and worker handoff each have cache locality, load balancing, and cross-thread queue trade-offs.
- Handlers must have bounded work to avoid blocking the event loop with CPU tasks or blocking calls; heavy work should go to a controlled executor with results safely posted back to the owner loop.
- High performance is not just about the event API; connection ownership, buffer lifecycle, backpressure, timer complexity, syscall batching, and error paths more often determine stability.

#### `io_uring`

**What is the model difference between `io_uring` and `epoll`?**

- **[OS/allocator]** `io_uring` submits operations and receives completions through shared submission/completion rings, reducing some syscall and context-switch overhead; it is closer to a completion-oriented interface.
- Not all operations, kernel versions, filesystems, and devices have the same asynchronous capability; some paths may fall back to kernel workers or have different restrictions.
- Registered buffers/files, fixed resources, multishot, and SQPOLL can reduce overhead but add pinning, resource accounting, deployment privilege, and lifecycle complexity.
- When completions arrive, user objects, buffers, and cancellation state must still be valid; "the request has timed out" does not mean the kernel will stop writing to the buffer.
- Whether it beats epoll depends on operation mix, batching, payload, kernel, security policy, and existing frameworks. Must benchmark — no API worship.

#### Zero-Copy

**Does "zero-copy" truly mean not a single copy?**

- It usually means reducing user/kernel CPU copies, context switches, or data path hops — not that there is absolutely no data movement in NIC, DMA, page cache, and protocol stacks.
- **[OS/allocator]** Linux `sendfile` can transfer between kernel-managed file/socket paths; `splice` moves references between supported descriptors/pipes; `MSG_ZEROCOPY` and similar capabilities have their own completion and buffer-reuse contracts.
- `mmap` avoids explicit read copies but access still causes page faults, and introduces mapping lifetime, SIGBUS, dirty/writeback, and address-space management.
- TLS, compression, application framing, or payload modification may make pure file-to-socket paths inapplicable; modern TLS/kernel offload support must also be verified per target environment.
- Zero-copy reduces certain CPU costs but may add page pinning, completion bookkeeping, small-message overhead, and tail latency.

#### Backpressure, Buffers, and Connection State

**Why must high-performance services have backpressure?**

- When producers continuously outpace network/clients, unbounded output queues turn throughput problems into memory exhaustion and long tails.
- Both per-connection and global queue/byte budgets, high/low watermarks, pause-reading, rejecting, degrading, or disconnecting policies are needed.
- Buffer owners must live until async operations confirm completion; scatter/gather I/O only copies descriptors and does not automatically own application buffers.
- Timeouts must distinguish connect, TLS handshake, request header/body, upstream, write, and idle; a single total timeout is hard to locate and govern.
- Slowloris, oversized frames, connection churn, and accept overload all require protocol limits and resource budgets.

#### Multithreaded Network Models and Performance Validation

**Does multithreading always improve network throughput?**

- Multiple loops can utilize multiple cores, but shared connection maps, allocators, timer wheels, accept queues, and metrics counters may form contention.
- `SO_REUSEPORT`, accept handoff, RSS/RPS, CPU affinity, and NUMA locality are Linux/deployment optimizations whose effects depend on kernel/NIC/topology.
- Cross-thread fd migration loses locality and adds synchronization; fixed owner loops are often simpler, but hot connections may be unevenly loaded.
- Measure requests/s, P50/P99/P999, CPU cycles, syscalls, context switches, run queue, packet loss/retransmit, queue depth, and memory separately.

### Follow-Up Questions

1. When a TCP `recv` returns only half a header, how does the state machine preserve progress and prevent malicious lengths?
2. After a non-blocking `send` writes only part of the buffer, how does the next writable event continue?
3. Why does epoll edge-triggered usually need to drain to `EAGAIN`? If a handler hands off to a worker mid-way, who is responsible for rearming?
4. After an fd is closed and quickly reused, how do old queued events avoid mishandling the new connection?
5. What happens when blocking DNS, disk I/O, or user callbacks are called in a Reactor loop?
6. Before an io_uring completion returns, can the request object and buffer be freed? How do timeout/cancel races converge to a single completion?
7. Why might registered buffers reduce overhead yet also increase pinned-memory risk?
8. Why might `sendfile` lose applicability with application compression or user-space TLS?
9. What CPU, copy, fault, pinning, and latency metrics should a "zero-copy" solution measure?
10. After the output queue reaches the high watermark, what feedback loop does continuing to read requests create?
11. In a one-loop-per-core plus worker pool hybrid, who owns connection state, and how do results return to the owner?

### Common Misconceptions

- Treating TCP as a message queue, assuming one read/write is a complete request
- Treating `EAGAIN` as a connection error, or not handling partial writes and half-close
- Believing epoll is an asynchronous completion API where no real read/write is needed after events arrive
- Edge-triggered reading only once without draining to `EAGAIN`
- Only calling close without handling fd reuse and queued event generation/lifetime
- Claiming io_uring is purely asynchronous on all kernels/operations and inherently faster
- Freeing buffers still potentially used by completions after request timeouts
- Literally interpreting zero-copy as no copying anywhere in hardware or kernel
- Having no per-connection/global backpressure and relying only on machine memory to absorb slow clients
- Looking only at peak QPS without tail latency, CPU, retransmits, queues, and memory

### Identity Difficulty

- **Intern/Campus hire**: Can explain byte streams, partial I/O, non-blocking, epoll readiness, Reactor, and basic framing.
- **Junior/intermediate C++ developer**: Can implement connection state machines, ET drain/rearm, buffer ownership, timeouts, and backpressure.
- **Senior/staff C++ developer**: Can compare epoll/io_uring/zero-copy kernel boundaries, design cross-thread ownership and single-completion semantics, and optimize based on end-to-end metrics rather than chasing QPS alone.

## 8. Engineering Troubleshooting and Performance Analysis

### Basic Questions and Answer Points

#### Core Dumps and Scene Preservation

**What is the first step after a process crashes?**

- First preserve raw evidence: core, exact executable, shared libraries, build ID, debug symbols, startup arguments, environment, container image, kernel/runtime logs, and crash timeline.
- **[OS/allocator]** Whether a core is generated depends on shell/resource limits, core pattern, service manager, container policy, dumpability, disk, and security settings; just running `ulimit -c unlimited` may not cover systemd/container environments.
- Do not recompile over the production binary first. Same source but different compiler flags, LTO, dependencies, strip, and layout can make backtraces misleading.
- Cores may contain secrets, request bodies, and user data; collection, transfer, and retention must comply with permissions and regulations.

**Can signals directly indicate the root cause?**

- `SIGSEGV` indicates an invalid memory access class result — could come from null/UAF/out-of-bounds/stack overflow/corrupted return address — it does not equal "null pointer".
- `SIGABRT` commonly comes from explicit abort, assert, allocator detection, or `std::terminate`; check stderr and the terminating exception.
- `SIGBUS`, `SIGILL`, `SIGFPE`, etc. must also be analyzed with fault address, instruction, and platform causes.
- Signals are symptom entry points. Final conclusions need stack, registers, memory, sanitizer, or reproduction evidence.

#### GDB Debugging

**What is the basic evidence chain for analyzing a core?**

```bash
gdb /path/to/exact-binary /path/to/core
(gdb) info threads
(gdb) thread apply all bt full
(gdb) frame 0
(gdb) info registers
(gdb) x/16gx ADDRESS
(gdb) disassemble /s
(gdb) disassemble /r START_ADDRESS, END_ADDRESS
(gdb) info line *ADDRESS
```

- First confirm executable, core, shared libraries, and symbols match, then look at the crashing thread and all threads.
- In optimized builds variables may be optimized out, frames inlined, tail-called, or reordered; `disassemble /s` is for mixed source mapping, combined with `/r`, explicit address ranges, and `info line *ADDRESS` to cross-reference real instruction bytes with source mapping — source lines cannot be treated as the sole execution order.
- The first frame of a corrupted stack may not be the root cause; UAF/overflow often happened long before the crash — combine allocator/sanitizer, watchpoints, or record/replay.
- Multi-threaded hangs need all threads, lock owners, futex waits, and application progress — do not look only at the current thread.

#### Valgrind and Sanitizers

**What are ASan, TSan, and UBSan each good at?**

- AddressSanitizer instruments to detect many heap/stack/global out-of-bounds, use-after-free, and other memory errors; it cannot prove all lifetime/logic errors are absent.
- ThreadSanitizer detects data races and some synchronization misuse; overhead is significant and it usually isn't combined with ASan in the same build.
- UndefinedBehaviorSanitizer detects many configured classes of UB such as certain integer, alignment, vptr, and shift issues; recover/trap mode affects runtime behavior.
- LeakSanitizer, often integrated with ASan, detects unreachable allocations; unbounded caches that are semantically still reachable are not treated as leaks.
- Sanitizers must cover real code paths and preserve symbols; custom allocators, assembly, prebuilt libraries, and unsupported platforms create blind spots.

**When is Valgrind still valuable?**

- Valgrind/Memcheck can check invalid access, uninitialized use, and leaks in some scenarios without recompiling everything, suited for supported platforms with acceptable high-overhead offline reproduction.
- It works through a different mechanism, generally much slower than compile-time sanitizers; SIMD/JIT/syscall support and platform availability need confirmation.
- The tools are not mutually exclusive: CI sanitizers, offline Valgrind, allocator diagnostics, and core analysis cover different blind spots.

**How to read sanitizer reports?**

- Read the error class and fault access first, then allocation/free/creation stacks — not just the final crash stack.
- The first report is usually closer to the root cause; secondary corruption from continued execution can create noise.
- Symbolizer, frame pointer/debug info, suppressions, and third-party library versions affect readability.
- Do not suppress unconditionally to "clear the report"; every suppression needs an owner, reason, and expiration condition.

#### `perf` and CPU Performance

**How to start from evidence when CPU is high?**

```bash
perf list
perf stat -e cycles,instructions,branches,branch-misses,cache-references,cache-misses -p PID -- sleep 30
perf record -F 199 -g -p PID -- sleep 30
perf report
```

- `perf stat` observes cycles, instructions, IPC, branch misses, and cache misses with an explicit, time-bounded event set; event availability and meaning still depend on CPU, kernel, and permissions.
- TLB event names are platform-dependent; first use `perf list` to see events supported on the target machine, then select explicitly with `-e`; you cannot claim default `perf stat` always provides TLB data with uniform names.
- `perf record/report` uses sampling to locate hot paths; frequency and duration must balance overhead with representativeness.
- Call graph quality depends on frame pointers, DWARF unwind, inlining, JIT symbols, and stripped binaries; missing stacks do not mean functions have no cost.
- CPU flame graphs represent aggregated sampled on-CPU stacks, not wall-clock or blocked time directly; I/O/lock problems need off-CPU, scheduler, futex, or tracing evidence.

**What to ask before optimizing a hot function?**

- Is it truly on the critical path of the target workload, and is the sampling share stable?
- Does the cost come from instructions, branch mispredictions, cache misses, allocation, lock contention, or syscalls?
- After optimization, are throughput, tail latency, CPU, memory, and correctness all re-verified?
- Has the compiler already inlined/vectorized, and does the change introduce code bloat, false sharing, or worse locality?

#### Production Crash, Hang, and Performance Regression Processes

**How to turn troubleshooting into a reusable process?**

- Define the phenomenon and metric definitions: crash rate, hang, CPU, RSS, latency, error rate; establish first-occurrence time and change correlation.
- Obtain minimal but complete evidence: version/build ID, traffic, thread/core/profile, allocator/kernel/container metrics.
- Propose falsifiable hypotheses; use sanitizers, targeted logging, fault injection, replay, or bisection to verify.
- After fixing, add regression tests, runtime guards, metrics, and rollout/rollback conditions — avoid only fixing the scene.
- Performance regressions use the same hardware, frequency policy, dataset, warm-up, concurrency, and statistical methods; a single benchmark number does not constitute a conclusion.

#### Compiler Diagnostics and Observability Construction

**How can Release builds balance performance and debuggability?**

- Keep separate debug symbols, build IDs, and symbol archives; binaries can be stripped but symbols must be accurately retrievable per version.
- Evaluate the cost of retaining frame pointers vs observability benefits; conclusions differ by architecture/unwinder.
- Crash handlers can only perform minimal async-signal-safe operations; complex symbolization and allocation go to external collectors or post-mortem analysis.
- Structured logging, request IDs, and metrics should not allocate unboundedly on hot paths; observability code also needs backpressure and privacy policies.

### Follow-Up Questions

1. Service has core limit set but still no core — which conditions of core pattern, service manager, container, and disk should be checked next?
2. Why must the exact executable, shared libraries, and build ID be preserved instead of just the source commit?
3. The top frame in a core is `memcpy` — how to determine whether the root cause is source/destination lifetime, length corruption, or an earlier heap overwrite?
4. When variables in an optimized build are "optimized out", what register, assembly, DWARF, and reproduction evidence can continue the analysis?
5. Why are ASan and TSan usually run in separate builds, and what does each miss?
6. LeakSanitizer reports nothing but RSS keeps rising — what allocator/non-heap/queue evidence to check next?
7. When is Valgrind still worth using despite being slow?
8. perf shows high cycles but low IPC — from which directions of memory stall, branch, lock, and scheduling to verify?
9. The CPU flame graph doesn't show much request latency — why supplement with off-CPU or scheduler evidence?
10. After fixing a crash, how to design a regression test that proves it captures the root cause rather than accidentally not crashing?
11. Why is calling complex loggers, `malloc`, and symbolizers directly in a signal handler dangerous?
12. A local benchmark shows 20% improvement — why can't this directly be published as a production performance conclusion?

### Common Misconceptions

- Saving only the core without the exact binary, libraries, symbols, and build ID
- Concluding null pointer on `SIGSEGV` and assert on `SIGABRT`
- Looking only at the crashing thread's first frame without checking other threads, allocation/free stacks, and earlier corruption
- Treating optimized-out variables or incomplete backtraces as unable to continue analysis
- Believing one sanitizer run proves no UB/data races/leaks exist
- Mass suppressing sanitizer reports to make CI green
- Treating Valgrind, ASan, TSan, and UBSan as fully equivalent tools
- Looking only at flame graph width without distinguishing on-CPU, off-CPU, sampling bias, and unwind gaps
- Only optimizing the widest function without looking at cache, locks, syscalls, and tail latency
- Executing non-async-signal-safe complex logic in crash handlers
- Directly comparing benchmark numbers from different hardware, loads, and warm-ups

### Identity Difficulty

- **Intern/Campus hire**: Can read basic backtraces; knows the purpose of cores, debug symbols, ASan/Valgrind, and perf.
- **Junior/intermediate C++ developer**: Can build crash evidence chains, choose ASan/TSan/UBSan, analyze multi-threaded hangs, heap corruption, and CPU profiles.
- **Senior/staff C++ developer**: Can build build-ID/symbol pipelines, low-risk production profiling, allocator/kernel joint evidence, and reproducible experiments, and turn fixes into guards, tests, and rollout standards.

3. Who owns connection/buffer/timer in a Reactor?
4. Under what operations/kernels might io_uring benefit, and when does it regress?
5. What kind of copying does zero-copy reduce, and what new lifecycle/completion costs does it add?
6. How does backpressure limit per-connection and global memory?
7. When P99 worsens, how to combine core/GDB, Sanitizer, perf, off-CPU, and allocator stats?
8. How does optimization get proven with the same workload and rollout guards?

Senior candidates should string together API mechanisms, ownership, resource budgets, and evidence chains — not just list epoll, io_uring, sendfile terms.

### Follow-Up Questions

1. After a candidate answers "pointers are 8 bytes on 64-bit machines", how to check boundary awareness with function pointers, target ABI, and capability architectures?
2. After a candidate says "references don't occupy memory", how to continue with reference members and calling conventions without confusing abstract semantics?
3. After a candidate says "inline prevents duplicate definitions", how to probe token-equivalent definitions, macros, and inline variables?
4. After a candidate draws a vtable, how to probe whether the standard mandates it, multiple inheritance adjustment, and constructor dispatch?
5. After a candidate says "Rule of Five", how to judge whether they truly understand Rule of Zero and exception guarantees?
6. After a candidate says "shared_ptr atomic count so it's thread-safe", how to construct a pointee data race?
7. After a candidate recites vector 2× growth, how to probe the amortized proof and implementation freedom?
8. After a candidate says "placement new doesn't allocate memory", how to probe old lifetime, alignment, destruction, and `launder`?
9. After a candidate hardcodes the `mmap` threshold, how to have them distinguish language, libc allocator, and kernel?
10. After a candidate says "atomic is lock-free so it's fast", how to probe runtime lock-free, wait-free, ABA, and contention?
11. After a candidate says "epoll is async I/O", how to distinguish readiness, completion, and actual read/write?
12. After a candidate says "zero-copy has no copies", how to probe DMA, page cache, TLS, and buffer completion?
13. After a candidate gets a core and only looks at the current stack, how to guide building a binary/symbol/thread/allocation evidence chain?

### Common Misconceptions

- Follow-ups only adding obscure nouns without digging along the same invariant, lifetime, or evidence chain
- Substituting specific x86-64, Itanium ABI, libstdc++, or glibc behavior for all C++ implementations
- Testing only whether candidates can recite standard clause numbers, not whether they can write safe APIs and verification methods
- Mistakenly judging "knowing common structures of vtable/control block/vector growth" as "knowing what the standard guarantees"
- Campus hire questions directly requiring lock-free reclamation, io_uring kernel paths, and perf counters — identity difficulty mismatch
- Senior candidates only asked syntax trivia without testing ownership, ABI, concurrency proofs, and production troubleshooting
- Deducting points for qualifying conditions in answers while rewarding absolute conclusions with no applicable scope
- Treating unassessed directions as unknown, or using one obscure question to cover an entire capability dimension

### Identity Difficulty

- **Intern/Campus hire**
  - Core: pointers/references/`const`, storage duration, construction/destruction, virtual, RAII, common containers, mutex/condition variable, basic sockets, and GDB.
  - Passing boundary: basic standard semantics correct; can identify dangling, double free, iterator invalidation, and data races; willing to add qualifications to implementation details after hints.
  - Not required: reciting ABI layouts, allocator thresholds, lock-free reclamation, or specific kernel internal paths.
- **1-3 year C++ backend**
  - Core: ODR/linkage, Rule of Zero/Five, exception guarantees, smart pointer ownership, STL complexity/invalidation, memory order basics, Reactor/backpressure, Sanitizer/perf.
  - Passing boundary: can independently fix lifetime/concurrency bugs, explain tool evidence, and qualify conclusions by target standard/library/platform.
- **Senior C++ backend**
  - Core: object lifetime, ABI, multiple inheritance, allocator/pmr, atomic publication, ABA/reclamation, io_uring/zero-copy trade-offs, production crash and performance evidence chains.
  - Passing boundary: can design low-coupling ownership and cancellation, give failure/progress/compatibility arguments, and reject pseudo-optimizations through experiments.
- **Staff/infrastructure track**
  - Core: cross-compiler/dynamic-library ABI, memory resource architecture, lock-free correctness, kernel I/O capabilities, NUMA/cache/allocator, observability, and progressive rollout.
  - Passing boundary: not only explains mechanisms, but clearly defines contracts, applicable scope, degradation paths, resource budgets, validation metrics, and long-term maintenance costs.
  - Bonus: proactively converting unknown implementation details into executable verification, such as target-specific layout dumps, symbol inspection, sanitizer matrices, litmus tests, allocator profiles, and kernel capability probes.
